# Webhooks والـAPI العام

> المرحلة 6 — §11.4 من خارطة الطريق (الخطوة الأولى في ترتيب التكاملات).

---

## 1. لماذا هذه الخطوة أولاً

ترتيب §11.4 يضع Webhooks وREST قبل Zapier وقبل HubSpot وقبل Salesforce.
السبب: هذه الخطوة تجعل **كل** تكامل لاحق ممكناً بيد العميل — Zapier
وMake وأي نظام داخلي لا نعرفه — بينما وصلة مباشرة إلى مزوّد واحد تخدم
مستخدمي ذلك المزوّد وحدهم.

نبدأ بما يفتح الباب لا بما يخدم اسماً.

## 2. مفاتيح الـAPI

### ما يميّزها عن كل مورد سبقها

**المفتاح لا ينتهي بتسجيل خروج ولا يظهر في سجل دخول.** عضو يغادر
المؤسسة تُلغى عضويته فيُقفل بابه في اللحظة نفسها؛ مفتاح نسخه أحدهم إلى
حاسوبه الشخصي يبقى يعمل إلى أن يلاحظه إنسان في قائمة.

ولذلك:

| الضابط              | التفصيل                                                     |
| ------------------- | ----------------------------------------------------------- |
| الصلاحية            | `integrations:manage` — للمالك وحده في البذرة               |
| العرض               | مرة واحدة عند الإصدار. لا مسار يعيده                        |
| التخزين             | `SHA-256` للمفتاح كاملاً. لا قيمة صريحة في قاعدة البيانات   |
| البادئة             | مخزَّنة صريحةً: تميّزه في السجلات ولا تكفي لاستخدامه         |
| آخر استخدام         | يظهر في القائمة — مفتاح صامت منذ شهور سؤالٌ يطرحه من يقرأها |
| الإبطال             | إبطال لا حذف، حتى يبقى السجل قابلاً للقراءة بعد أسابيع      |

**لماذا SHA-256 لا bcrypt** خلافاً لكلمات المرور: هذا سرّ عشوائي بـ256
بت لا كلمة يختارها إنسان. لا قاموس يخمّنه، والتجزئة البطيئة تكلفة على
كل طلب بلا مقابل أمني.

### الشكل والنطاقات

```text
nmq_<بادئة 8>_<سرّ 64>
```

الترميز ست عشري لا base64url: أبجدية base64url تحوي `_` وهو نفسه فاصل
المقاطع، فمفتاح من كل ثلاثة كان يُقرأ بأربعة مقاطع ويُرفض بلا سبب مفهوم.

النطاقات **مستقلة تماماً عن صلاحيات المستخدمين ولا تُشتق منها**:
المفتاح يمثّل نظاماً لا شخصاً، ويعيش في ملف إعداد على خادم عميل. منحه
صلاحيات دور «مسؤول» كان يعني أن تسريب ملف إعداد يساوي تسريب حساب
مسؤول.

| النطاق            | يفتح                                     |
| ----------------- | ---------------------------------------- |
| `contacts:read`   | `GET /api/v1/integration/contacts`       |
| `contacts:write`  | `POST /api/v1/integration/contacts`      |
| `events:read`     | `GET /api/v1/integration/events`         |
| `cards:read`      | محجوز لمسارات لاحقة                      |

### الاستخدام

```bash
curl -H "x-api-key: nmq_..." https://api.nomiqa.om/api/v1/integration/contacts?since=2026-08-01T00:00:00Z
```

**لا ترويسة مؤسسة**: المؤسسة تُشتق من المفتاح نفسه ولا تُقبل من الطلب —
نفس مبدأ اشتقاقها من الـslug في المسار العام (القاعدة 17).

مسار المفتاح يعمل **بدل** سلسلة (Auth0 → عضوية → صلاحية) لا بعدها،
ويتخطاه `Auth0JwtGuard` و`TenantContextGuard` صراحةً. أما التعليق فيمر
على `SuspensionGuard` نفسه: المؤسسة المعلَّقة تقرأ ولا تكتب، بالمفتاح
كما بالجلسة.

### المسارات

| المسار                            | الملاحظة                                       |
| --------------------------------- | ---------------------------------------------- |
| `GET /integration/contacts`       | مرتّب تصاعدياً بوقت الالتقاط، مع `since` للتزايد |
| `POST /integration/contacts`      | **يتطلب سند موافقة صريحاً** — راجع أدناه        |
| `GET /integration/events`         | الفعاليات وأعداد عملائها                       |

الترتيب تصاعدي لا تنازلي: المزامنة التزايدية تمرّر آخر ما رأته في
`since`، وترتيب تنازلي كان يجعلها تفقد ما بينهما عند أول صفحة ثانية.

الحقول **صريحة محدودة لا تمرير لصف قاعدة البيانات**: عمود يُضاف غداً لا
يجوز أن يظهر في تكامل عميل بلا قرار. و`message` — نص كتبه زائر لصاحب
البطاقة وحده — ليس منها.

### الكتابة تحتاج سنداً

```json
{
  "fullName": "…",
  "email": "…",
  "consent": { "granted": true, "basis": "form on acme.om/contact", "marketing": false }
}
```

`basis` مطلوب ويُخزَّن كما هو مكان إصدار نص الموافقة. السبب: **نحن لا
نعرف كيف حصل ذلك النظام على البيانات**. اختراع سند من عندنا توقيعٌ على
إقرار لا نملك ما يسنده، وتركه فارغاً صفُّ بيانات شخصية بلا سند — وهو ما
تمنعه القاعدة 16.

## 3. Webhooks

### العقد

| العنصر            | القيمة                                            |
| ----------------- | ------------------------------------------------- |
| الطريقة           | `POST` بجسم JSON                                  |
| الوجهة            | **HTTPS فقط**، ولا عناوين داخلية                  |
| `x-nomiqa-signature` | `HMAC-SHA256` ست عشري                          |
| `x-nomiqa-timestamp` | ثوانٍ منذ الحقبة                               |
| `x-nomiqa-event-id`  | معرّف الحدث — أساس تجاهل المكرر                 |

```text
signature = HMAC_SHA256(secret, "<timestamp>.<raw body>")
```

الطابع الزمني **داخل المُوقَّع لا بجانبه**: توقيعٌ على الجسم وحده يبقى
صالحاً إلى الأبد، فمن التقط تسليماً قديماً أعاد إرساله متى شاء. النافذة
المقبولة عند المستقبِل خمس دقائق (`WEBHOOK_TIMESTAMP_TOLERANCE_SECONDS`).

الصيغة بسيطة عمداً: كل لغة تنفّذها بثلاثة أسطر، ومستقبِلٌ لا يستطيع
التحقق سهولةً لن يتحقق أبداً. ودالة التحقق موجودة في شيفرتنا مختبَرةً
(`webhook-signature.ts`) حتى يبقى المثال مطابقاً لما نوقّع به فعلاً.

### مثال تحقق عند المستقبِل

```js
const expected = createHmac('sha256', secret).update(`${timestamp}.${rawBody}`).digest('hex');
const fresh = Math.abs(Date.now() / 1000 - Number(timestamp)) <= 300;
const valid = fresh && timingSafeEqual(Buffer.from(expected), Buffer.from(signature));
```

### الأحداث المتاحة

`contact.captured` · `card.published` · `invoice.paid` ·
`subscription.activated` · `subscription.canceled`

مجموعة فرعية من أحداث الـOutbox لا كلها: حدث داخلي كـ`membership.revoked`
يصف تنظيم المؤسسة لا عملها، وبثّه توسيعٌ للسطح بلا طلب.

### التسليم مرة واحدة على الأقل

الفريد على (وجهة، حدث) في قاعدة البيانات يمنع إنشاء تسليمين للحدث
نفسه. لكن **التسليم قد يصل مرتين** — إعادة محاولة بعد مهلة استجابة
مثلاً — ولذلك يحمل كل نداء `x-nomiqa-event-id`: تجاهُل ما عولج مسؤولية
المستقبِل، وهي مسؤولية رخيصة بمطابقة قيمة واحدة.

### إعادة المحاولة والإيقاف الآلي

| العنصر         | القيمة                                        |
| -------------- | --------------------------------------------- |
| المحاولات      | 6                                             |
| التأجيل        | `2^n` دقيقة حتى ساعة                          |
| مهلة النداء    | 10 ثوانٍ                                       |
| الحجز          | دقيقتان — يمنع نسختين من الـWorker من التسليم معاً |
| الإيقاف الآلي  | بعد 20 إخفاقاً متتالياً على الوجهة              |

الإيقاف يُعلَن في الشاشة بسببه، وإعادة التفعيل بتعديل الوجهة. وجهة فشلت
عشرين مرة متتالية ليست وجهة تتعافى، وكل حدث لاحق يضيف صفاً إلى طابور
لن يفرغ — والصمت بلا إعلان أسوأ من التوقف.

### الحمولة

تُبنى **داخل سياق المؤسسة** لا من حدث الـOutbox: أحداث الـOutbox تحمل
معرّفات فقط منذ المرحلة 3 لئلا تمر بيانات شخصية عبر Redis، وما يحتاجه
نظام العميل هو الحقول نفسها. تُقرأ عند البثّ وتعيش في صف التسليم حتى
يُسلَّم.

```json
{
  "id": "<event id>",
  "type": "contact.captured",
  "createdAt": "2026-08-19T09:00:00.000Z",
  "data": { "id": "…", "fullName": "…", "eventId": "…", "qualifiers": {} }
}
```

المبالغ في حمولات الفوترة **بالبيسة أعداداً صحيحة**: القسمة على ألف قبل
الإرسال تُدخل عدداً عشرياً في عقد منشور، وهو أول باب لخطأ تقريب عند
العميل.

## 4. منع النداء إلى الداخل (SSRF)

مسار يقبل عنواناً من مستخدم ثم **يناديه خادمنا** هو تعريف الثغرة.
عنوان كـ`https://169.254.169.254/…` يجعل خادمنا يقرأ بيانات اعتماد
السحابة ويسلّمها لمن كتب العنوان.

الضوابط:

- HTTPS فقط.
- رفض `localhost` و`*.internal` وكل مدى خاص: `10/8`، `127/8`،
  `169.254/16`، `172.16/12`، `192.168/16`، `100.64/10`، و`fc00::/7`.
- `redirect: 'error'` عند الإرسال: وجهة تعيد 302 إلى عنوان داخلي تلتف
  على الفحص كله.

الفحص على الاسم لا على ما يحلّه: المحلّل قد يعيد عنواناً داخلياً بعد
الفحص (DNS Rebinding). الحماية الكاملة في الإنتاج بوابة خروج مضبوطة،
وهذه الضوابط تغلق الحالات المباشرة.
